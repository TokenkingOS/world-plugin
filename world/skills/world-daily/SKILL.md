# 每日进展写进本体（world-daily）

一次运行先由第 0 步脚本给出的 `mode` 定走哪条路。`write`（没有 `capture_switch`，包括其他所有同事）：收集今天的进展，包括今天开过的会上定下的结论 → 对每个目标对象按四段记一条外部事件，有新增的再写一条引用它的状态快照 → 汇报写了什么。`check_only`（本人已切换到本机采集）：会话里的变化由本机采集逐条记进 world，这里只查漏、提醒，不写事件和快照。会议事件由天枢写，本 skill 不记（2026-10-20 定）。写入只用插件 world 连接的 `world_*` 工具。事件和快照记在这条连接登录的本人名下（一人一枚人凭证）。快照读侧都标为未经确认。

载荷模板在 [references/payloads.md](references/payloads.md)，写入前先读它。会议怎么找、会上的结论怎么并进日进展，在 [references/meetings.md](references/meetings.md)。设定时任务看 [references/scheduling.md](references/scheduling.md)。

## 不做的事

- 不碰凭证。凭证只由插件连接的登录提供：不读取、不打印、不复制 `agent.token`；事件与快照里不出现任何凭证、密码、token。
- 只记外部事件、写状态快照。不做承诺、确认这些门，不指派、不建对象、不修订对象、不记开始与交付、不提出问题。
- 不记确认完成、重开，也不记验收，写进展时也不建议本人去补记这些。scope 升级到 tkos.world/0.3 以后，Task、Mission 的完成只由对象 DRI 本人确认，Activity 交付即关闭，没有「待验收」；进展里照实写事实，例如「交付了什么，待 DRI 确认完成」。
- 不记会议事件（`category: meeting`）。会议事件统一由天枢写：主持人或创建人在天枢整卡确认后，天枢记一条整场会议事件（2026-10-20 定）。会上定下的进展照常写进日进展，见 meetings.md。
- 不自己判断本人切没切换到本机采集：走哪条路只认第 0 步脚本输出的 `mode`，不看持续来源有没有启用，也不凭会话或记录推断。`capture_switch` 只在本人当时明确同意切换后才写进 `daily.json`（见「切换到本机采集」），建配置时不顺手加。`mode` 为 `check_only` 时不写日进展事件和状态快照。
- 日进展只写配置里列出的目标对象。只写工作事实。和工作无关的内容不写；不整段照抄会话或聊天原文，长内容给链接；不写别人的私事。
- 不编造。会话和资料里没有的进展不写；拿不准归哪个目标的，不写。

## 收集范围

日进展只写公司工作的进展（方法侧 2026-10-22 的写法）：

- **纳入**：当天实际开展、且和配置里列明的本人负责的公司经营目标、Mission 及其相关 Task 直接相关的工作，包括围绕这些任务开展的分析、讨论、会议协作、文档或代码产出、验证与问题处理。会话里没有直接提到目标或 Mission 的名字，只要能明确判断和这些任务有关，也纳入。
- **不纳入**：和这些公司任务没有直接关系的个人项目、其他公司的项目、其他团队独立开展且和本人负责的任务无关的项目，以及和公司任务无关的学习与练习。
- **怎么判**：按工作内容和公司任务的实际关联判，不按会话在哪个工具（Codex、Claude Code 等）、哪个本机目录。判断不了和公司任务有没有关联的，不写进日进展。

配置里的 `session_dirs` 只决定读哪些目录下的会话（见「配置」），不决定算不算进展：读到的会话照样按上面三条判，没读到的会话里的工作这次就收不到。

## 配置

`~/.tkos-world/daily.json`（Windows 是 `%USERPROFILE%\.tkos-world\daily.json`）：

```json
{
  "person": {"name": "张三", "principal_id": "<本人的 principal id>"},
  "work_calendar": "cn",
  "targets": [
    {"object_id": "<Mission 或目标的对象 id>", "title": "<标题，方便人看>"}
  ],
  "feishu_open_id": "<可选：本人的飞书 open_id，读飞书时用>",
  "extra_sources": ["<可选：别的本地来源，例如「读 ~/日报/今天.md」>"]
}
```

不想让日进展读到某些会话的（例如本机还有个人项目、其他公司的项目），可以另加一项 `"session_dirs": ["~/TKOS", "~/work/tkos-*"]`：只读工作目录在这些目录或其子目录下的会话，条目可以用 `*`、`?` 通配；不写就读本机当天的全部会话。收集脚本自己读这一项。目录只缩小读取的范围，算不算进展仍按「收集范围」判；公司任务的工作也散在别的目录里的，那些目录要一并写上，否则读不到。目录照本人说的写，不要自己猜。它在 skill 目录外，插件更新换 skill 时不会冲掉；不要改脚本来过滤。

`work_calendar` 不写时是 `cn`：按中国法定节假日与调休选工作日。本人国内放假也照常工作的，用 `"work_calendar": "weekdays"`：保留周一至周五的记录与补写，忽略国内放假和周末调休。**已经在 `~/.tkos-world/daily.json` 里写了 `"work_calendar": "weekdays"` 的人，升级技能时保留这一项。** 明确指定日期的补写始终优先，即使那天是假日或周末也照写。日历来源、字段和定时安排见 [references/scheduling.md](references/scheduling.md#日历与触发频率)。

`capture_switch` 是可选的切换状态：本人已切换到本机采集时才有，形状和写入流程见「切换到本机采集」。没有它就是 `write`，照常写日进展；写了但形状不对，第 0 步的脚本报错停下，不会当作没切换。

提示里写了「定时运行」就是定时任务在跑，没人可问；否则当作本人在场。

没有这个文件时先建，要和本人确认；定时运行时什么都不写，汇报「缺 ~/.tkos-world/daily.json，请先手动运行一次」。工具读不出「我是谁」，所以先问。

1. 问一次本人的名字。提示里已经给了名字、要写的对象 id 或 principal id 的，直接用，不再问。
2. 按名字找本人负责的对象，依次找：本月的 Mission（`world_list_objects`，`type` 为 `Mission`，`period` 为本月 `YYYY-MM`），没有就找本月的周期目标（`type` 为 `PeriodGoal`），再没有就找责任单元（`type` 为 `ResponsibilityUnit`）。对候选逐个 `world_get_object`，看 `identity` 里的责任人是不是本人；找到的列给本人，确认写哪几个。
3. 找不到本人负责的对象（例如本人是单元成员、责任人是别人）：直说没找到，请本人给出要写的对象 id 和自己的 principal id（管理员那里有）。不要按会话内容把别人负责的对象推荐给本人。
4. 本人给的对象 id 先 `world_get_object` 核对存在。`person.principal_id` 取责任人里本人的 principal id，本人给了就用给的；`person.name` 用本人的名字。
5. 问一次要不要只读某些目录下的会话：本机还有个人项目、其他公司的项目，不想让日进展读到的，请本人说出做公司任务的那些目录，照着写进 `session_dirs`；在别处开的工作树、Codex 应用里新开对话的目录（例如 `~/.codex/worktrees`、`~/Documents/Codex`）里也做公司任务的，一并写上。告诉本人：写了以后，别的目录里的会话就不读了，哪怕和公司任务有关。不需要就不写。
6. 写好文件，给本人看一眼内容。

## 每次运行

### 0. 定下写哪一天，走哪条路

- 先找 Python，下文写作 `<python>`：
  - macOS：`~/.tkos-world/venv/bin/python`，没有就用 `python3`。
  - Windows（PowerShell）：`"$env:USERPROFILE\.tkos-world\venv\Scripts\python.exe"`，没有就用 `py -3`；运行时前面加 `&`。
  - 都没有就停下，汇报「world-daily（写日报和只查漏）都要 Python；没有就先用 world-record 在对话里记」。只查漏也要先跑下面的选日脚本，所以也停在这里。
- 再用 `<python>` 运行 `<skill 目录>/scripts/collect_sessions.py --select-dates`，读取返回的 JSON；此模式调用 `scripts/select_dates.py`，按本机日期与 `daily.json` 的 `work_calendar` 选日，并按 `capture_switch` 给出 `mode`。这一步只选日期和走哪条路，不收集会话、不写文件；失败就停下汇报（`capture_switch` 写错了也在这里报错，不会当作没切换），收集与写入都留到选日成功后。
- `mode` 只认脚本的输出，不自己判断，也不看持续来源有没有启用。`check_only`：`daily.json` 里有合法的 `capture_switch`，本人已切换到本机采集，走下面的「只查漏」，不做第 1 到 4 步。`write`：没有 `capture_switch`，包括其他所有同事，照常做第 1 到 4 步写日进展。
- 本人指定了日期（「补写 10 月 8 日的进展」），给脚本加 `--date 2026-10-08`：只处理返回的 `date`，不受节假日过滤，也不自动补别的日期；`mode` 照样按配置给出，不看那天是哪天。
- 否则 `date` 为 `null` 表示按本人的日历今天休息，只汇报跳过，不收集、不写入，两条路都一样。`date` 不为空时，`check_only` 只查 `date` 这一天，不看 `previous_workday`；`write` 先检查返回的 `previous_workday`，再写 `date`；上一个工作日可以跨长假、跨年，不自行按星期或限制回看天数。
  1. 查 `previous_workday` 写过没有：对第一个目标 `world_get_events`，`since` 为那天 00:00，找 `【日进展】<姓名> <那天日期>`。没写过，就先补写那天；写过了不补。调休周末也按日历处理，例如 `cn` 的 2026-10-12 补 10-10，10-08 补 09-30；`weekdays` 的 10-08 仍补 10-07。
  2. 再写今天。只有现在早于 12:00、而上一个工作日这次要补写（补写时有没有进展都算）时，这次不写今天：今天的事多半还在后头，现在写了，明天再跑时今天已算写过、不会再补，后来的进展就丢了。留给晚上的运行或明天的补写，汇报里说一句。
  3. 只补这一个工作日。连着漏了几天的，更早的请本人点名补写。
- 补写的那天和今天各走一遍第 1 到 3 步，先补写，第 4 步一起汇报、按天分开列；每一天只有真实业务新增才记事件和必要快照；无新增不记，已写过的以「补充」再写，定时运行不问人。下文的「今天」都指正在写的这一天。写的不是今天时：收集会话加 `--date <那天>`，读飞书的 `--start`、`--end` 取那天 00:00 与 23:59，`world_get_state` 采用资料已核的事实截至时刻；事件与快照保留来源实际时刻，未知时形成待核事项。

### 只查漏（`mode` 为 `check_only`，代替第 1 到 4 步）

下面用到的 `world_app_sources_list`、`world_app_sources_runs`、`world_app_sources_imports` 和其余工具一样，来自插件的 world 连接（本人应用面 `/app/mcp`）。

已切换的人，会话里的变化已由本机采集逐条记进 world，同一项工作只记一次：日终不再从原始会话另提一遍，不写四段日报事件和日报快照，只核、只报、只提醒。**这一路不调用 `world_record_event`、`world_refresh_state`**，也不调用别的写工具。核不了、出错、选择失效时也不转去做第 1 到 4 步写日报。定时运行没人可问，提醒写进汇报；本人在场就当面说。

- **核选择仍有效**：`world_app_sources_list` 读本人当前公司的选择与准确 `history`，找到 `daily.json` 里 `capture_switch.selection_id` 的那一个。核它没有被撤销或换版、本人当前的角色还在、已确认的历史范围还在。
- **核覆盖与待处理**：用这个 `selection_id` 调 `world_app_sources_runs`、`world_app_sources_imports`，分页读到底：覆盖观察与最后完整检查（覆盖到何时）、原处理结果、还有多少条待整理、待本人处理的项。日终检查已确认起点以来全部缺口、失败和待本人项；本机组件沿原计划和进度补传，不把范围滑到昨天。提交响应未知先读原结果，不能换 key 重做。
- **找采集没盖到的公司工作**：照第 1 步的命令收 `date` 这一天的本机会话，再对照选择里的来源和上一项的覆盖截止，列出公司工作落在覆盖之外的：另一个 Agent 的会话、配置 `session_dirs` 里采集没读的目录、覆盖截止之后才发生的工作。是不是公司工作按「收集范围」判；判断不了会话在不在覆盖内的，列为「未确认覆盖」，不当作已覆盖。每条写清做了什么、在哪个会话，不整段照抄。`previous_workday` 不另收会话，它的缺口看覆盖截止。飞书和 `extra_sources` 这一路不读。
- **提醒**：对上一项列出的，请本人用 `world-record` 在对话里主动记，或决定要不要扩大采集的来源。本 skill 不替本人记，也不替本人扩大采集。
- **有问题照实报，不写日报**：选择失效（撤销、换版、角色变化）、历史范围未确认、覆盖有缺口、后台整理停了（最后完整检查太旧，或待整理的条目一直不减）、解析失败、来源当前不可达，都按真实原因与处理人写进汇报。旧回执只证明当时覆盖，离线电脑的新材料仍是未知；不得把无运行记录当无工作。`world_app_sources_*` 不可用或报错同样停下汇报。
- **汇报**：开头写「本次只查漏，没有写日进展事件和快照」，并注明切换时刻（`capture_switch.confirmed_at`）。然后分开列：选择是否有效（`selection_id`）；覆盖到何时；待整理多少条、待本人处理的项（各是什么、谁处理）；采集没盖到的公司工作；出错或跳过的原因。已经收到、待本人、独立核验分别汇报。没有缺口也没有待处理时，只汇报核对结果，不补造「今天无新增」的事件。

以下第 1 到 4 步是 `write` 的路。

### 1. 收集今天的进展

- 本机会话（必做）：用第 0 步找到的 `<python>` 运行本 skill 目录下的 `scripts/collect_sessions.py`：
  - macOS：`<python> <skill 目录>/scripts/collect_sessions.py`
  - Windows（PowerShell）：`& <python> <skill 目录>\scripts\collect_sessions.py --out "$env:TEMP\tkos-daily.md"`，再读这个文件（直接打印中文可能乱码）。

  `<skill 目录>` 是本 skill 所在的文件夹。输出是这一天（本机时区）每个 Codex、Claude Code 会话的工作目录、你的请求与每轮最后的答复，已截断、疑似密钥已隐去；日进展任务自己的运行（包括这一次）已略去，同一会话里前后的工作照列。读到的会话按「收集范围」判，和公司任务无关的整段不用。配置里没有 `session_dirs`、读到的会话里有个人项目或其他公司的项目的，汇报里提醒本人一句：不想让日进展读到这些，可以在配置里加 `session_dirs`。
- 配置里的 `extra_sources`。
- 飞书（可选）：本机有 `lark-cli` 并已以用户身份登录、配置里有 `feishu_open_id` 时，读今天你自己发的消息：`lark-cli im +messages-search --as user --sender <feishu_open_id> --start <今天 00:00，带时区> --end <现在，带时区> --page-all --format json --no-reactions`。只取和目标对象有关的事实与文档链接。读不了就跳过，不要为此申请授权或改权限。
- 会议（可选）：本机有 `lark-cli` 并已以用户身份登录时，按 [references/meetings.md](references/meetings.md) 第 1、2 节列出今天开过的会、读妙记摘要。读不了就跳过，不要为此申请授权。
- 有人当面让你写时，最后问一句「还有没在会话里的进展吗？」；定时运行不问。

### 2. 按目标对象整理

对每个目标对象，按方法侧的日进展模板（《Daily Progress 模板及质量标准》v1）整理成四段。日进展是周复盘、月度复盘的事实输入，不是当天的完整复盘，也不要求每天得出新判断：

- **00｜今日摘要**（必写）：1–2 句，结论先行，从下面三段提炼，不引入它们没有依据的新结论。没有可验证的新增结果时，写当前推进到哪一步，不写「整体良好」。
- **01｜关键进展与结果**（每天检查，有实质内容才展开）：今天实际完成、验证或推进了什么，相比原来的预期结果有什么变化。每条写清结果到了哪一层（Activity、阶段交付、Outcome 不能混），还没证明什么也写上。证据紧跟在这一条后面：链接或来源（哪个会话、哪份文档、哪条消息）和时间；证据只给出处，不整段照抄会话或聊天原文。
- **02｜关键问题与不确定性**（按需）：今天出现或进一步明确的问题与偏差、有具体迹象的风险、还判断不了的关键未知。写清事实、相对预期的差异和影响；已知原因写清，未知不强行归因。已经存在、今天没有新信息的问题不必复述，也不能当作已经解决。
- **03｜关键协同与待决事项**（按需）：今天新增或变化的、要别的责任主体配合或判断的事：要谁提供什么、对方已知的响应或承诺状态；要哪个有权的角色判断什么，现在是未提交、已提出、待决还是已决定。不凭猜测补交付日；今天新定或改了的安排注明来源，不重抄原有的 Mission、Task Plan 或 Mission Card 上的日期。正式 scope 里写职责，不写真名。

通用规则：

- 只记有意义的增量：新增结果、重要阶段进展、问题变化、判断变化。不做流水账：发了哪条消息、开了哪张票、读了什么材料这些动作不写。
- 事实与解释分开：你自己的初步解释在句末标「（Agent 初步判断）」；只有来源里本人或 DRI 明确说过的，才写成已确认的判断。
- 看不到不等于没有：你只看得到本机会话和配置里的来源。某一段没有可写的内容时，写「在已覆盖来源中未见」，不写「无」。
- 不替业务方做正式确认：承诺变更、Agreement、对象状态变化照实写成「待 <谁> 确认」，不写成已生效。
- 和哪个目标都对不上的事实不写。
- 目标当天已由本机采集逐条记过的事实不再写进 01，核法见第 3 步第 2 小步。
- 某个目标没有业务新增，不新增事件或快照。读不到、解析失败的来源写明缺口与处理人；不能据此判断无工作。新增的实际阻塞或未解决情况仍是业务事实，按其来源和时点处理。

本人在场时，先把每个目标的四段列给他看，他说可以再写，他改了就按改的写；定时运行直接写。

### 3. 写入

会议事件不在这里记，由天枢写。会上定下的结论，已按 [references/meetings.md](references/meetings.md) 第 3 节并进第 2 步的四段（结果进 01，要别人配合或判断的进 03）。只有真实新增的目标对象依次写入，没有新增的不写：

1. `world_get_object`：记下 `business` 组的 `object_id`、`version` 与对象类型。引用写成 `<object_id>@<version>`：`version` 是修订序号；同组的 `object_version` 是并发版本，和它不必相等，不能写进引用。对象已关闭或已取消时跳过它，在汇报里提醒本人更新配置。生命周期带 `upgraded_from`（不为 `null`）的，是 scope 升级到 0.3 时停在「已交付」或「调整中」的对象，快照的当前状态照实写，例如「升级前已交付，待 DRI 确认完成」「升级前被退回在改」。
2. `world_get_events`（`since` 为今天 00:00，带时区）：如果已有内容以 `【日进展】<姓名> <今天日期>`（日期写成 `YYYY-MM-DD`）开头的外部事件，说明今天写过了。没有新事实就跳过这个对象；有新事实就照常再写一组，事件第一行改成 `【日进展·补充】<姓名> <日期>`。同一次分页读全的事件里，`content.text` 是 JSON 且 `format` 为 `world-source-evidence/0.1` 的，是本机采集已经逐条记下的事实，不算日进展事件，也不必再记：只看发生在正在写的这一天的，把第 2 步 01 里和它们说的是同一件事的条目去掉，比对 `value`、`quote`、`field_key` 和事件的发生时刻，对不上的不去。去掉以后这个对象没有新事实，就跳过它。汇报里写「已由本机采集记过 N 条，未重复」。
3. `world_get_state`：读最新快照，作为新快照的底稿（没有就从空白开始）。
4. `world_record_event`：按模板第 1 节。记下返回的 `event_id`。
5. `world_refresh_state`：按对象类型选模板，Mission、Task、Activity 用第 2 节 `execution_state`，周期目标与长期目标用第 3 节 `goal_state`，责任单元用第 4 节 `unit_state`。`source_event_refs` 放上一步的 `event:<event_id>`，以及第 2 步读到的、今天这个对象上类别为 `meeting` 的事件（多半是天枢记的）。新快照按第 5 节由上一条合成：别人的组件和问题组件原样带上，只换你自己的进展条目 `daily:<principal_id 前 8 位>`。四段的去处：`current_state` 用 00 的摘要；进展条目（目标与单元是 `progress` 文字）写 01；02，以及 03 里会影响结果的依赖，写进 `blockers`（执行状态）或 `key_risks`（目标、单元状态）。问题组件不新增。
6. 记下快照的 `object_id`。

事件 `occurred_at` 取本次新增事实已核实的原发生时刻，快照 `as_of` 取事实截至时刻，均带时区。汇总中逐项保留来源与各自时刻；不以运行时刻、文件 mtime 或补写日的固定钟点替代。必要时拆分不同事实；时间未知就留待核事项。`period` 取事实所属月份 `YYYY-MM`。

### 4. 汇报

逐个目标列出：事件 id、快照 id；无新增的写明没写；读不到的来源写明缺口；本机采集已记过的写「已由本机采集记过 N 条，未重复」；跳过的写明原因（今天已写过且没有新内容、对象已关闭、出错）。会议另列：今天参加过的会（主题与妙记链接），以及目标对象上已有的会议事件的 id（见 meetings.md 第 4 节）。本 skill 不记会议事件。配置里的目标都不是本月的时，提醒本人更新配置。定时运行时这就是这次运行的结果。

## 切换到本机采集

下面核前提用到的 `world_app_sources_*` 同样来自插件的 world 连接；连接不可用时，前提核不了，不写 `capture_switch`。

切换是一项显式配置：`~/.tkos-world/daily.json` 里有 `capture_switch`，第 0 步的脚本就给出 `check_only`；没有就是 `write`。Agent 不得自己判断已切换，也不因为本人启用了持续来源就当作已切换。

```json
"capture_switch": {"confirmed_at": "<本人同意切换的时刻，带时区>", "selection_id": "<本人在 world 确认的本机采集来源选择 id>"}
```

只在本人提出要切换时做；定时运行没人可问，什么都不写。流程：

1. **逐条核前提**，每条把结果（齐、不齐、未核实）和依据报告给本人：
   - 采集来源已启用，且覆盖原来 `session_dirs` 里做公司工作的会话：用 `world_app_sources_list` 看选择的来源与 `history`，再对着 `session_dirs` 的每个目录说明哪些在覆盖内、哪些不在，没写 `session_dirs` 的按本机全部会话说。Codex 和 Claude Code 都做公司工作的，两边的会话都要被某个选择覆盖，或由本人明确只用一个。
   - 后台自动整理在运行：用 `world_app_sources_runs`、`world_app_sources_imports` 看最后完整检查和最近的整理结果是不是新近的，待整理的条目有没有在减。
   - 按人汇总视图可用：实际读一次本人这几天的进展汇总，确认是按人汇总、带来源和事实时间的；读不到或拿不准的写「未核实」，不当作齐了。
   - 配置里有 `feishu_open_id` 或 `extra_sources` 的，一并告诉本人：切换后日终不再读它们，这些来源里的工作要用 `world-record` 在对话里主动记；本人知道并仍要切换才继续。
2. **前提有不齐或未核实的**：说清缺什么、谁来补，不写配置，到此为止。
3. **前提都齐了**，问本人要不要现在切换。只有本人在本次对话里明确同意，才把 `capture_switch` 加进 `daily.json`：`confirmed_at` 取本人同意的时刻（先跑 `date`，带时区），`selection_id` 取上面核过的那个选择，其余配置不动；写完给本人看一眼。
4. **提醒本人**：原来的日进展定时任务不会因此停掉，它之后每次运行都只查漏、不写日报；要不要停用它，由本人另行确认，这里不代停，也不改定时任务。
5. 本人明确要求退回写日报时，删掉 `capture_switch` 这一项。已有的日进展记录不动。

## 出错怎么办

- `HTTP_UNAVAILABLE`：返回里带着 `idempotency_key`，用同一个键原样重放一次；还不行就停下汇报，不要换新键再写。
- 503 `SERVICE_BUSY`：服务忙，什么都没提交，返回里有 `retry_after_seconds`，写入另带 `idempotency_key`。等够这些秒，读原样重试，写用同一个键原样重放；仍忙就按新给的秒数再等，最多三轮，之后停下汇报，不要换新键再写。503 `EVIDENCE_UNAVAILABLE` 不是忙（证据存储或数据库不可用），没有等多久的说法：重试一次仍不行就停下汇报。
- 422 `INVALID_REQUEST`：按报错改载荷，再试一次。常见原因：空块写成了 `{"text": ""}`（应省掉这个块）；照抄的组件多了 `ref` 字段，或 `refs`、`scope` 还是读回的结构而不是字符串；时刻比写入时刻晚。
- 403：这枚凭证写不了这个对象的快照：Agent 凭证要在对象所在的域持 AGENT，本人的人凭证要本人是这个对象或它主干上某一级的责任人。事件写成了就保留，在汇报里说明，请本人找管理员。
- 404：对象 id 不对或看不到。汇报，请本人检查配置。
- 409 `VERSION_CONFLICT` 或引用被拒：对象刚出了新版本，重新 `world_get_object` 取版本号再写。
- 事件写成、快照失败：不要再记一条事件，修好快照后引用同一个 `event_id` 重写快照。
- 409 `PROTOCOL_BINDING_CONFLICT`、`PROTOCOL_NOT_SUPPORTED` 或 `PROTOCOL_WRITE_DISABLED`：连接认的契约版本和 scope 的对不上，多半是 scope 刚升级。停下，不要重试，汇报「scope 的契约版本变了」：请本人重启 Codex 或 Claude Code，让插件连接重新认 scope 的版本（见 [references/scheduling.md](references/scheduling.md)）。
- 工具不可用、world 连接连不上或要求重新登录：停下，汇报「world 插件连接不可用」，不要改 MCP 配置。
- `mode` 为 `check_only` 时 `world_app_sources_*` 不可用、报错或选择失效：停下，按真实原因和处理人汇报，不改去写日报，不改 MCP 配置。
